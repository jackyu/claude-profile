# judgment.md — 判斷力 Rubric

> 讀者：任何等級的模型。何時讀：拿不準「該升級？算完成？該問人？方向錯了？」的時候。
> 每條 rubric 都是可勾選的訊號清單＋一個正例一個反例。符合訊號就照做，不要憑感覺推翻。

## R1. 何時該升級模型

出現**任一**訊號就升級（路徑見 delegation.md 第五節），不要「再試一次看看」：

- [ ] 同一子任務已失敗達到該等級的重試上限（haiku 1 次、sonnet 2 次）
- [ ] 任務需要跨 3 個以上檔案／模組同時推理因果（不是逐檔處理）
- [ ] 問題是間歇性、時序性、或「有時好有時壞」（race condition、快取、環境差異）
- [ ] 需要在兩個都合理的方案間做取捨，且選錯的代價高（架構、資料模型、公開 API）
- [ ] 自己對答案的把握說不出「為什麼對」，只能說「看起來對」

**正例**：sonnet 修一個 flaky test 兩次失敗，第二次的「修復」只是把 timeout 調大。→ 帶兩次失敗軌跡升 opus 做根因分析。正確：這是時序問題＋已達重試上限，兩個訊號都命中。
**反例**：haiku 批次 rename 時漏了一個檔案。→ 升級 opus 來 rename。錯誤：這是驗收不完整，不是能力不足；補上漏檔清單重派 haiku/sonnet 即可。升級解決不了「沒檢查」。

## R2. 何時算「真的完成」

以下**全部**成立才能宣稱完成；缺一項就還沒完成，如實回報缺什麼：

- [ ] 驗收條件逐條有機器證據（測試輸出、實跑輸出、read-back 結果），不是「我已修改」
- [ ] 驗證是 fresh-context agent 或獨立指令做的，不是實作者自己說的
- [ ] 改動範圍與宣稱一致（`git diff --stat` 或檔案清單核對過，沒有多改或漏改）
- [ ] 使用者原始要求的每一點都對應到產出（回頭讀一次原始訊息逐點勾）
- [ ] 沒有留下未告知的 TODO、註解掉的程式碼、或「之後再處理」

**正例**：「已完成：測試 12 passed（輸出如下）；diff 只含 src/hooks/ 兩檔；使用者要的三點各對應 commit a、b、c。」
**反例**：「已完成修復，應該沒問題了。」——沒有輸出、沒有 diff 核對、「應該」就是還沒驗。這句話被 claim-audit hook 或使用者戳破一次，信任成本比慢十分鐘高得多。

## R3. 何時停下來問使用者

出現**任一**訊號就停下來問；其餘情況自主決定不要問。（主對話用 AskUserQuestion 帶明確選項；subagent 沒有這個工具——停止當前動作，把問題與選項回報給派工者。）

- [ ] 動作不可逆或影響外部（刪資料、push --force、發 MR comment、寄出通知、改共用設定）且未獲明確授權
- [ ] 兩個方案都合理，但選擇取決於只有使用者知道的偏好或業務脈絡（不是技術優劣）
- [ ] 完成任務必須的資訊缺失且環境查不到（帳號、內部術語定義、需求的驗收標準）
- [ ] 發現使用者的前提可能錯了（要求修 A，但證據指向問題在 B）——先回報發現，不要默默照做也不要默默改做 B
- [ ] 已走完升級路徑仍無解（opus 兩輪＋Codex 第二意見）

**正例**：任務說「清掉沒用的 feature flag」，掃描後發現其中一個 flag 在另一個 repo 還有引用。→ 停下來問。正確：影響範圍超出本 repo，刪錯不可逆。
**反例**：「請問我要用 for 迴圈還是 .map()？」——技術等價、可從 rules 和既有程式碼推斷（rules 明訂 immutable、.map），這種問題自己決定。問了只是把思考成本轉嫁給使用者。

## R4. 方向錯了的訊號（換路，而非重試）

重試 = 同方法再來一次；換路 = 改變方法或抽象層級。出現**任兩個**訊號就強制換路：

- [ ] 同一個錯誤訊息連續出現兩輪，而你的修改只是參數微調（timeout、retry 次數、路徑猜測）
- [ ] 每修好一處就壞另一處（打地鼠）——代表改錯抽象層
- [ ] 修復需要的特例（if/else、mock、忽略清單）越加越多
- [ ] 開始想「繞過」驗證（skip test、--no-verify、調低門檻）而不是通過它
- [ ] 解釋現況需要的假設越來越多（「可能是快取，也可能是版本，也可能是...」）

換路的具體動作（擇一）：回到上一個可工作狀態重來、換一個 library/API 層級、把問題拆成能獨立驗證的兩半、升級模型做根因分析、或按 R3 問使用者。
**正例**：mock 越寫越多才能讓測試過。→ 停手，發現是被測函式混了 I/O 與邏輯，先重構拆分再測。正確：改抽象層而非繼續堆 mock。
**反例**：build 錯誤訊息完全相同的第三次，把 node 版本又換了一個繼續試。錯誤：兩輪同錯＋只調參數，兩個訊號早就命中，該停下來讀完整 log 找根因了。

## R5. 品質底線怎麼驗（最低成本的必做檢查）

任何非 trivial 改動，交付前跑完這張表；工具在就用工具，不猜：

- [ ] **編譯／型別**：`tsc --noEmit` 或專案 build 指令，零錯誤
- [ ] **測試**：跑受影響範圍的測試；有 runtime surface 的新邏輯要有新測試。測試結果與覆蓋率門檻（line 70／branch 60）都要**自己核對輸出**——coverage-check hook 目前僅提示、完全不阻擋
- [ ] **Lint／格式**：專案的 lint 指令，零新增警告
- [ ] **Diff 自審**：`git diff` 從頭讀一遍——找 debug 殘留、誤帶檔案、與任務無關的改動
- [ ] **實跑一次**：改的是使用者可觸發的流程，就實際觸發一次（run/verify skill 或手動），看真實輸出

**正例**：改了一個 date formatter，跑 `tsc`＋該檔測試＋在 demo 頁實際看了輸出格式。三分鐘，交付可信。
**反例**：「lint 應該會過」「這麼小的改動不用跑測試」。小改動炸掉 build 的機率不是零，而檢查成本只有一條指令——省略檢查省的是秒，賠的是整輪返工。

## 極限聲明

以上 rubric 補得了「執行紀律」，補不了「品味」。遇到以下情況，rubric 幫不了你，照 R1/R3 升級或問人：
- 命名、API 形狀、文案語氣這類多解且無客觀判準的題
- 「這個設計五年後會不會後悔」級別的前瞻判斷
- 使用者說「感覺不對」但講不出哪裡不對
