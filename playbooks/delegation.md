# delegation.md — 模型調度守則

> 讀者：主對話的協調模型（任何等級）。何時讀：要派工、選模型、寫委派 prompt 時。
> 模板見 `templates.md`；升級與停損的判準見 `judgment.md`。

## 一、指揮官不下場

主對話的 context 是最貴的資源，只放：決策、結論、`檔案:行號`、下一步。以下動作**一律派 subagent**，不親自做：

| 動作 | 派給 |
|---|---|
| 讀超過 2 個檔案、或單檔超過 ~300 行 | `Explore`（唯讀搜尋）或 `general-purpose` |
| 掃 repo 找模式／找所有呼叫點／盤點結構 | `Explore` |
| 查網頁、讀文件、多來源研究 | `general-purpose`（可用 WebSearch/WebFetch） |
| 批次改檔（rename、套 pattern、格式化） | `fast-worker` |
| 寫功能、修 bug、寫測試 | `code-implementer` |
| 根因分析、架構取捨、演算法設計 | `deep-reasoner` |
| 第二意見、卡關救援 | Codex（`codex:rescue` skill） |

主對話**可以**親自做的：讀單一小檔確認關鍵事實、跑一兩條短指令、改 1–2 個檔案的小 edit、與使用者對話。判準：這個動作會不會把大量原始內容灌進主 context？會 → 派工。

## 二、派工三件套（每個委派 prompt 必含）

1. **目標與動機**：要做什麼、為什麼（subagent 看不到主對話，動機能讓它在邊界情況做對取捨）。
2. **驗收條件**：可機器檢查的完成定義（「測試 X 通過」「回報每個結果附 檔案:行號」「diff 不超出 Y 目錄」），不是「做好做滿」。
3. **回報格式**：明訂回什麼、不回什麼（見下方回報合約）。

三件套缺一，先補齊再派。模板在 `templates.md` 直接填空。

## 三、模型名冊（2026-07-04 實測，不憑印象）

**Agent tool 的 `model` 參數只接受**：`sonnet`、`opus`、`haiku`、`fable`。
**Agent tool 沒有 effort 參數**——派工時無法指定推理深度；需要更深推理就升 model 等級。（effort 選項只在 Workflow 工具的 `agent()` 內存在，且 Workflow 需使用者明確要求多代理編排才可用；你的環境沒有 Workflow 工具就別找它。）

| subagent_type | 預設 model（frontmatter） | 用途 |
|---|---|---|
| `Explore` | 繼承 session | 唯讀搜尋、盤點（找得到程式碼，但不做審查） |
| `Plan` | 繼承 session | 實作規劃 |
| `general-purpose` | 繼承 session | 研究、多步驟雜項 |
| `fast-worker` | sonnet | 機械性、低模糊度任務 |
| `code-implementer` | claude-sonnet-5 | 實作撰寫（TDD） |
| `deep-reasoner` | opus | 推理密集 |

- 要覆寫等級時傳 `model` 參數（例：把 fast-worker 升到 `opus` 重試）。`fable` 未來環境不可用，制度不依賴它。
- 純機械且量大（如批次 rename 上百檔）可試 `model: "haiku"` 壓成本，但先用一小批驗證品質再放量。

## 四、回報合約（寫進每個委派 prompt）

- 只回：結論、關鍵證據（`檔案:行號` 或指令輸出摘要）、明確的未完成事項。
- 不回：整檔內容、完整 diff、探索過程流水帳。
- 長產物（報告、大 diff、清單）**落檔**到 scratchpad 或指定路徑，回報只給路徑＋三行摘要。
- 回報若與主對話已知事實矛盾，以可直接觀察的證據為準；subagent 的「推論」不等於「事實」，重要結論要求它附驗證方式。
- **完成即交報告**：委派 prompt 必須明訂「完成後先用 SendMessage 送出完整報告、再結束回合」——idle 通知不等於已交報告，主對話不負責催收。（2026-07-29 實測：單一 session 內 3 個 agent 全數 idle 而未交報告，共催收 4 次。）
- **裁決要逐項回執**：中途送給 subagent 的重要裁決（改規格、覆寫先前指示）用獨立訊息送達，並要求對方在下次回報中逐項確認已套用；訊息可能亂序或晚到，plan approval 的 feedback 欄位不可依賴。（2026-07-29 實測：兩次裁決各被跳過一輪，靠驗收才補救。）

## 五、升降級路徑

計數原則：**counter 綁定「模型等級」，升級後計數重開**。各等級做錯上限：haiku 1 次、sonnet 2 次、opus 2 次、Codex 1 次；整條升級鏈走完（最多 6 次派工）仍無解 → 停下來問使用者。「做錯」才計入；「做對但有遺漏」（如批次任務漏幾筆）不算失敗，補上明確清單可重派原等級。（CLAUDE.md 鐵律「3 次卡關即停」管的是**自己動手**的停損，與本節的派工鏈 counter 是兩套，各管各的。）

- **haiku 做錯一次** → 直接升 sonnet 重派，不重試 haiku。
- **sonnet 做錯一次** → 修 prompt 再試一次；**連錯兩次** → 帶完整失敗軌跡（原 prompt、兩次輸出、錯在哪）升 opus（`deep-reasoner` 或 `model: "opus"`）。
- **opus 連錯兩次** → 帶完整失敗軌跡找 Codex（`codex:rescue`）第二意見；仍無解 → 問使用者（見 judgment.md R3）。
- **降級**：高階模型解出「模式」後（例：確立一個轉換寫法），把模式寫成明確規格，降回 sonnet／haiku 批次套用剩餘工作。
- 同一等級的上限用完不是「再試一次」的訊號，是「方法錯了」的訊號——升級時同時考慮換路，判準見 judgment.md R4。

## 六、驗證不自驗

寫的人不驗自己的東西。驗收一律派 **fresh-context agent**（新 context、沒看過實作過程）：

| 產物類型 | 驗法 |
|---|---|
| 檔案／文件改動 | read-back：新 agent 讀檔，對照驗收條件逐條檢查，回報通過/不通過＋證據 |
| 程式碼 | 測試或實跑：跑測試貼輸出；無測試就實跑主流程貼輸出。「看起來對」不算過 |
| 高風險判斷（架構、資安、不可逆操作） | 第二意見：另派一個 opus 或 Codex **獨立**解同一題（不給它第一個答案），比對結論；分歧處就是風險所在 |
| 多方案擇優 | 產生 2–3 個獨立方案，派一個 judge agent 依明確評分準則選優並說明理由 |

高風險決策的標準流程（沿用既有慣例）：讓 deep-reasoner（opus）與 Codex **並行**解同一問題、互相看不到對方答案，主對話綜合兩者最佳部分。

## 七、並行原則

- 互相獨立的子任務，在同一則訊息裡一次派出（多個 Agent 呼叫並行），不要序列等待。
- 有依賴的子任務才序列派。拿不準有沒有依賴 → 當作有依賴，序列派（慢但不會做白工）。
