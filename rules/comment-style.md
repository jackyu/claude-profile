# comment-style.md

程式碼註解的句子表達規範。只管「怎麼寫」；該不該寫維持既有原則：只寫 code 本身講不出的限制。

## 適用範圍

- 所有程式碼內註解：`//`、`/* */`、`#`、JSX `{/* */}`
- JSDoc 保留 `@param`／`@returns` 等結構標籤，描述文字照樣適用本規範

## 表達原則

- 口語但專業：判準是「這句會不會在台灣的 code review 上被講出來？」不帶玩笑、不帶語氣詞
- 用行為描述取代名詞化黑話：寫「按下送出才驗證」，不寫「延遲驗證機制」
- 單句超過 40 字就拆開重組；中文習慣短句
- 刪重複或過度修飾的形容詞，一句能講完就不寫兩句

## 贅字清單（見到就砍或改寫）

「此處」「進行」「用於」「以確保」「該（函式／變數）」「對於…而言」「相關的」「必要的」「值得注意的是」「基本上」

## 用詞

避開中國用語（質量、默認、調用、接口、兜底、閉環），用台灣工程圈日常講法。

## BAD vs GOOD

- BAD：`// 此處進行防禦性檢查以確保資料完整性`　GOOD：`// 先擋掉空值，後面才不用一直判斷`
- BAD：`// 該函式用於將日期格式化為相關的顯示字串`　GOOD：`// 把日期轉成畫面要顯示的字串`
- BAD：`// 值得注意的是，當快取失效時系統將會自動地重新獲取資料並更新相應的狀態`　GOOD：`// 快取失效會自動重抓資料、更新狀態`
- BAD：`// 調用 API 接口獲取用戶數據`　GOOD：`// 打 API 拿使用者資料`
